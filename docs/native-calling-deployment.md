# Native calling deployment

This deployment runs the API, web application, engine, SIP edge and media service. Telnyx supplies the carrier connection. The application owns routing and media. Local acceptance is recorded in `plans/implementation-progress-2026-09-07.md`; it is not evidence of public-network or carrier acceptance.

## Configuration

Use a Linux host with a stable public IPv4 address and Docker Compose. Copy `.env.voice.example` to `.env.voice` and replace all example domains, addresses and credentials. Generate distinct random secrets. Runtime files are ignored by Git.

- Point the web domain at an HTTPS ingress forwarding to port 3100. Preserve WebSocket upgrades for `/api/v1/live` and session sockets. Set `AUTH_URL` and `API_APP_URL` to this public HTTPS origin.
- Point each organization's SIP domain at the SIP edge. Configure that domain in Settings before assigning phones. Each organization must have a unique domain; extension 1001 can then exist in several organizations.
- Install the SIP/TURN certificate chain and private key in `VOICE_CERTS_DIR`, which must be a path OUTSIDE the checkout (`/etc/optimiq/certs` in the template). `./config/certs` is the compose fallback for development and is the output of `config/certs/generate-dev-certs.sh` — a self-signed CA that browsers reject, regenerated by a script and gitignored as disposable. Certificate names must cover the WSS and TURN hostnames. SIPD runs as UID 1001 and must be able to read the files. Renew and restart the affected listeners when rotating certificates.
- Copy `config/turn/turnserver.conf.example` to its ignored runtime path. Its shared secret must match `PROVISION_TURN_SECRET`. Allow only the deployed media addresses as TURN peers. Coturn uses Linux host networking.
- Browser calling is one decision with three variables. `MEDIAD_WEBRTC=true` turns on mediad's ICE stack and, through `PROVISION_WEBRTC_ENABLED`, makes the API REQUIRE `PROVISION_SIP_WSS_URL` — it does not boot without one. `SIPD_WSS` derives from `MEDIAD_WEBRTC` in `compose.voice.yaml` unless set explicitly, so the SIP edge's WSS listener comes up with it. Set `MEDIAD_WEBRTC`, `PROVISION_SIP_WSS_URL` and the three `PROVISION_TURN_*` values together, or leave all of them off.
- Configure SMTP. Production signup requires email verification; the API refuses a production mail configuration that would log one-time links instead of delivering them.

The fresh-volume initializer creates `optimiq_voice`, `optimiq_pbx` and `optimiq_cdr`. It does not modify existing volumes. Existing installations must retain their actual database names in every URL.

## Web application: the live socket and the two deployment shapes

The browser talks to its own origin for everything: `next.config.mjs` rewrites `/api/*` and `/provision/*` to the API, which keeps the better-auth session cookie first-party. That rewrite is HTTP proxying and **does not carry a WebSocket upgrade**, so `/api/v1/live` — the feed behind the wallboard, the queue panel, the agent console and every live registration/active-call tile — cannot reach the API through it. Choose one of two shapes.

**Reverse-proxied (recommended, and what the compose deployment does).** One public origin serves the web application and forwards `/api/*` to the API with the `Upgrade`/`Connection` headers preserved. Leave `NEXT_PUBLIC_API_ORIGIN` and `NEXT_PUBLIC_AUTH_BASE_URL` unset; the socket is opened against the page's own origin and inherits the ingress. This is the shape the bullet in Configuration describes ("Preserve WebSocket upgrades for `/api/v1/live` and session sockets"), and the only one where a `wss://` upgrade rides the same certificate as the app.

**Split origins.** The web application and the API are served on different origins (a `next dev` workstation, or a static frontend deployment). Set `NEXT_PUBLIC_API_ORIGIN` to the API's origin — `http://127.0.0.1:3200` locally, `https://api.example.com` in a deployment — and the live socket is opened directly there, bypassing the rewrite. `NEXT_PUBLIC_AUTH_BASE_URL` is read as the fallback when it is already set for the auth client, since it names the same origin. Two things must line up or the upgrade is refused: the API's `trustedOrigins` (derived from `AUTH_URL` and `API_APP_URL`) must contain the **web** origin, because `live-gateway.ts` checks the handshake's `Origin` header against that list; and the session cookie must reach the API origin, which on a shared host and differing ports is automatic (cookies ignore the port) but across hostnames needs `AUTH_COOKIE_DOMAIN` and `AUTH_COOKIE_SAMESITE` configured for the pair.

Both variables are `NEXT_PUBLIC_*` and therefore **inlined at image build time**, not read at container start. A split-origin deployment must build the web image with them set.

## Database migration and runtime principals

The `migrate` job applies the auth, PBX, CDR and legacy API journals in order. It requires owner URLs, an explicit deployment stage and `DATABASE_MIGRATION_CONFIRM_PRODUCTION=apply` for production. The API waits for successful completion. Runtime service containers do not receive migration owner URLs.

Before the first API start, provision the three runtime logins in `.env.voice` using the database administration system. They must be dedicated non-superuser roles, with no database/role creation privileges. Grant connection, public-schema usage, table DML and sequence usage on their respective database. Grant the default privileges for future tables created by the migration owner too.

The current repository's PBX/CDR admin workers require an owner or BYPASSRLS principal. Use dedicated non-owner BYPASSRLS runtime roles for those two databases, and grant membership in `pbx_tenant_tls` / `cdr_tenant_tls` respectively. Request-scoped operations switch to these non-inheriting tenant roles and set the organization inside a transaction. Tenant roles must not receive BYPASSRLS, ownership or additional mutation privileges. The preflight checks this split at startup. Auth uses its separate base database. This admin-worker privilege is a current architectural requirement, not a claim that the application login itself is tenant-isolated.

Validate configuration without starting services:

```sh
docker compose --env-file .env.voice -f compose.yaml -f compose.voice.yaml --profile webrtc config --quiet
```

After reviewing the target databases and migration changes, run the migration job before starting the API. An existing installation needs a verified backup and restore procedure before applying migrations. The published `migrations` image is the `migrations` stage of `apps/api/Dockerfile`: the built workspace, no build toolchain, running as UID 1001. It carries the package migration runners and needs the workspace root, since `.scripts/migrate-platform.mjs` invokes each package's `scripts/migrate.ts` from there.

## Network paths

| Traffic         | Destination                | Notes                                                      |
| --------------- | -------------------------- | ---------------------------------------------------------- |
| Web application | HTTPS ingress → web:3100   | Keep API/NATS/DB private                                   |
| Phone SIP       | 5060 UDP/TCP or 5061 TLS   | Organization domain identifies the tenant                  |
| Browser SIP     | 8089 WSS                   | Valid public certificate required                          |
| Carrier SIP     | 5088 UDP/TCP               | Restrict ingress to Telnyx's documented signaling networks |
| Plain RTP/RTCP  | 30000–30999 UDP            | Advertised `MEDIAD_PUBLIC_IP` must be reachable            |
| WebRTC media    | 31000–31999 UDP            | ICE/DTLS/SRTP terminated by mediad                         |
| TURN client     | 3478 UDP/TCP, 5349 TLS/TCP | Expiring credentials supplied by the API                   |
| TURN relays     | 32000–32999 UDP            | Host firewall must preserve relay ports                    |

Telnyx connection configuration must direct inbound calls to the carrier listener. Configure the credential connection, outbound profile, numbers and inbound routes in the application. The carrier credential lookup is scoped to the organization's enabled trunk and checks the Telnyx connection username. API keys and SIP passwords are not carried through routing snapshots.

Use Telnyx's current [SIP trunking documentation](https://developers.telnyx.com/docs/voice/sip-trunking/get-started) and [network allowlist](https://developers.telnyx.com/docs/voice/sip-trunking/network-configuration/ip-whitelisting) when configuring carrier ingress. Verify the configured webhook URL ends in `/api/v1/carrier/webhooks/telnyx`.

## Observability: metrics and scraping

Every service exposes Prometheus metrics on a **private** listener that the public ingress must not
publish. The payload names call volume, registration counts, authentication failures and consumer
lag; together those describe a tenant's traffic closely enough to be reconnaissance, so they sit
beside `/healthz` and pprof rather than on the product's port.

| Service | Endpoint                         | Controlled by                                   |
| ------- | -------------------------------- | ----------------------------------------------- |
| sipd    | `http://<sipd>:9090/metrics`     | the health listener, `SIPD_HEALTH_ADDR`         |
| mediad  | `http://<mediad>:9091/metrics`   | the health listener, `MEDIAD_HEALTH_ADDR`       |
| api     | `http://<api>:9200/metrics`      | `API_METRICS_ADDR`, default `127.0.0.1:9200`    |
| engine  | `http://<engine>:9201/metrics`   | `ENGINE_METRICS_ADDR`, default `127.0.0.1:9201` |
| NATS    | `http://<nats>:8222/varz` `/jsz` | the broker's own monitoring port                |

There is no switch on the Go services: unlike pprof, which is a denial-of-service and a memory
disclosure and is why the health listener is private in the first place, a Prometheus registry
costs a handful of atomics per request and an endpoint nothing reaches unless it is scraped.

The two Node listeners bind loopback by default, which is right for a scraper running as a sidecar
and wrong for one on another host — set `API_METRICS_ADDR` / `ENGINE_METRICS_ADDR` to a private
interface in that case, and firewall it. Setting either empty turns that listener off. A bind
failure is logged and **not** fatal: an `EADDRINUSE` on the metrics port must not stop a process
that can otherwise carry calls.

```yaml
scrape_configs:
  - job_name: optimiq-voice
    scrape_interval: 15s
    static_configs:
      - targets: ["sipd:9090", "mediad:9091", "api:9200", "engine:9201"]
```

What each service publishes:

- **sipd** — `sipd_sip_requests_total{method}`, `sipd_sip_responses_total{method,status}`,
  `sipd_registrations_total{outcome}` (accepted / challenged / refused — a 401 challenge is the
  first half of every digest exchange and is deliberately not counted as a failure),
  `sipd_auth_failures_total{method}`, the three `sipd_auth_lockout_*` counters from the spray
  throttle, `sipd_dialogs`, `sipd_subscriptions`, plus the process and Go runtime collectors.
- **mediad** — `mediad_sessions`, `mediad_session_capacity`, `mediad_sessions_ended_total{reason}`,
  `mediad_rtp_packets_{received,sent}_total`, `mediad_rtp_packets_dropped_total{reason}`,
  `mediad_rtp_frames_suppressed_total{reason}` (suppression by playback/DTMF/hold/mute is NOT loss
  and is labelled apart from it), `mediad_playbacks_finished_total`,
  `mediad_recordings_finished_total`, `mediad_dtmf_digits_received_total`.
  **Per-session totals land when the session ENDS**, not as packets arrive — see the package header
  for why the packet path carries no counters — so a scrape during a long call sees it in the
  gauges and not yet in the totals.
- **api** — `api_http_request_duration_seconds{method,route,status}` (the route PATTERN and the
  status CLASS, never a URL or an exact code), `api_live_ws_clients` and the live-channel counters,
  `api_nats_consumer_pending` / `_ack_pending` / `_redelivered` / `_ack_floor` per durable, and
  Node's default collectors including `nodejs_eventloop_lag_seconds`.

- **engine** — `engine_active_channels`, `engine_channels_adopted_total`, `engine_draining`,
  `engine_sip_invites_total` / `engine_sip_admissions_total` / `engine_sip_refusals_total{reason}`
  (the reason is the `SipInviteRefusalReason` vocabulary; served minus admitted is NOT the refusal
  count, because an INVITE can be served and still be in flight), the readiness booleans
  `engine_media_ready` / `engine_signalling_ready` / `engine_nats_connected` / `engine_lease_held`,
  the adoption and stale-watch counters `engine_peers_lost_total`,
  `engine_sip_instances_lost_total`, `engine_channel_watch_adopted_total`,
  `engine_channel_watch_stale_recoveries_total`, `engine_routing_stale_recoveries_total`,
  `engine_routing_cached`, `engine_routing_invalidations_total`, the per-hop RPC series
  `engine_rpc_calls_total{plane,operation}` / `_failures_total` /
  `engine_rpc_latency_{p50,p99,max}_milliseconds`, and Node's default collectors under an
  `engine_` prefix including `engine_nodejs_eventloop_lag_seconds`.
  Every one of these is a scrape-time READ of a counter `/healthz` already reports, so the call path
  carries nothing new. Two consequences to know: the RPC quantiles are the bucket BOUNDS
  `RpcLatency` keeps and are per-instance, so they do not aggregate across a fleet the way
  `histogram_quantile` would (`engine_rpc_calls_total` beside them does); and a `+Inf` quantile
  means "slower than the last bound", which is an outage rather than a latency.

Two alerts are worth having before any others: `api_nats_consumer_pending` climbing on the `CDR`
durable while `api_nats_consumer_ack_floor` stops moving is the billing ledger falling behind, and
`nodejs_eventloop_lag_seconds` is the API's version of the single-core saturation already measured
on the engine.

On the engine, alert on any increase of `engine_channel_watch_stale_recoveries_total` or
`engine_routing_stale_recoveries_total` — the watch recovered, which is the point, but something
outside the process stopped flow-control replies — and on `engine_lease_held == 0`, which means
peers believe the instance is dead and may contest its live channels. Do not ROUTE on either;
`/healthz` deliberately does not degrade for them, for the reasons in `HealthController`.

**Not covered.** There is no tracing anywhere and no `ServiceMonitor` or dashboard in the
repository.

## Backups, restore and the retention runbook

Tooling lives in `.scripts/backup/`; its README carries the mechanics and the invocation. This
section is the policy.

### What is backed up

| Artifact         | Contents                                                                      |
| ---------------- | ----------------------------------------------------------------------------- |
| `pg-<db>.dump`   | `optimiq_voice`, `optimiq_pbx`, `optimiq_cdr` in `pg_dump` custom format      |
| `roles.sql`      | cluster roles and grants, **passwordless** (`pg_dumpall --no-role-passwords`) |
| `pg-<db>.counts` | per-table row counts at dump time, which the restore verifies against         |
| JetStream        | a broker snapshot per stream, or a store-directory copy with a caveat         |
| Objects          | recordings, voicemail, prompts, hold music, exports and branding              |

Four migration journals live in three databases: the auth and legacy-API journals share
`optimiq_voice`, the PBX journal owns `optimiq_pbx`, and the CDR journal owns `optimiq_cdr`.

Ownership and ACLs are deliberately kept in the dumps (`--no-owner` is **not** passed): the RLS
preflights assert them at boot, so a dump that dropped them restores a cluster the API refuses to
start against. Roles are dumped without passwords so the artifact carries no credential material —
the restore re-provisions the runtime logins from the target environment's own secrets.

### RPO and RTO

Both are properties of the SCHEDULE an operator chooses, not of these scripts. Stated for the
recommended shape — `backup.sh` from a nightly cron with the artifact set replicated off-host:

- **RPO — 24 hours for Postgres, and that is the number to improve first.** These scripts take
  logical dumps; there is no WAL archiving or PITR configured anywhere in this repository, so
  everything since the last dump is lost. A deployment that cannot lose a day of call records needs
  continuous archiving (`archive_command` to object storage, or a managed Postgres with PITR)
  alongside these dumps, and the dumps then become the portable copy rather than the recovery path.
- **RPO — near-zero for the object store**, if the S3 driver is in use with versioning on the
  bucket: recordings are immutable once written, so an hourly `objects-backup.sh` loses only
  recordings made in the last hour, and nothing is ever overwritten.
- **RPO — one backup interval for JetStream, with a caveat.** The streams hold in-flight work
  (legs not yet filed, voicemail not yet transcribed). Losing them loses those, not the ledger.
- **RTO — measured, on the rehearsal below: under a minute of script time** for a stack of this
  size, plus whatever the artifact set takes to reach the target host and whatever the
  orchestrator takes to start the services. The dominant term is transfer, not restore.

### Rehearsed, and the numbers

Both scripts were run end to end against the live local stack (three databases, 29 JetStream
streams, 65 206 messages, a 70-file object store) into disposable targets:

| Step                                               | Time  | Result                                                              |
| -------------------------------------------------- | ----- | ------------------------------------------------------------------- |
| `backup.sh` (3 DBs + JetStream + objects)          | 2.8 s | 13 MB artifact set, manifest verified                               |
| `restore.sh` into `*_drill` databases              | 2.3 s | 86 tables' row counts matched exactly                               |
| Smoke reads as the owner                           |       | 59 users, 1 748 extensions across 16 organizations, 3 909 call legs |
| Smoke reads as `voice_api`/`voice_pbx`/`voice_cdr` |       | identical counts — grants and RLS memberships intact                |
| JetStream store loaded by a scratch broker         |       | 28 of 29 streams, 65 551 messages, `CDR` 3 909                      |

The `CDR` stream's 3 909 messages against the restored ledger's 3 909 `call_legs` rows is the
cross-check worth keeping in the drill: it says the two halves of the same set describe the same
moment.

### What is NOT covered

- **Point-in-time recovery.** Logical dumps only; see the RPO note above.
- **The secrets.** `.env.voice`, the TLS material in `VOICE_CERTS_DIR`, the TURN shared secret and
  the NATS credentials are deliberately outside these artifacts. Back them up with whatever holds
  the rest of the deployment's secrets; a restore without them produces a cluster nothing can
  authenticate against.
- **MEMORY-backed JetStream state.** The `presence` KV bucket is not on disk and is not in either
  artifact. The engine re-applies it on reconnect, so the cost is a few seconds of stale busy lamps.
- **A running stack's in-flight calls.** A restore rebuilds state, not conversations.
- **Cross-version restores.** Match the `pg_restore` major version to the target server's; a newer
  client emits `SET` statements an older server rejects, which fills the log with benign errors.
- **Automation.** No cron entry, CronJob or compose service invokes `backup.sh`; scheduling it is
  the operator's step and there is nothing in the repository that does it for them.

### CDR retention

Two windows, enforced by two different mechanisms, and the difference is not cosmetic.

**Recordings — per organization.** `recordings.retentionDays` is an org setting (Settings →
Recordings, guarded by `recordings.configure`); `CDR_RECORDING_RETENTION_DAYS` is the platform floor
used when a tenant has not set one. Both default to `0`, meaning keep indefinitely. The window is
stamped onto the row when the recording is written, so changing the setting never re-stamps
recordings that already exist. `CdrRecordingRetentionSweeper` runs hourly under `CDR_WRITER_ENABLED`
and deletes the OBJECT first, then tombstones only the rows whose object actually went.

**Call records — platform-wide.** `call_legs` and `call_events` are partitioned by month so that
expiry is a `DROP TABLE`, and a partition holds every tenant's legs for that month. The window is
therefore the platform's and cannot be a tenant's: a shorter per-organization window would be a
batched `DELETE` against tables that are append-only _by privilege_, and a longer one is not
expressible at all once the partition is gone.

```
CDR_LEG_RETENTION_MONTHS=0        # 0 = keep for ever (the default, and it stays the default)
CDR_RETENTION_DRY_RUN=true        # the interlock; clear it only after reading a dry run
CDR_RETENTION_SWEEP_INTERVAL_MS=86400000
```

To turn it on: set the window, leave `CDR_RETENTION_DRY_RUN=true`, and read the
`CDR partition retention (DRY RUN)` line — it names every partition that would be destroyed, their
total size, and how many organizations hold rows in them. Only then clear the flag. Each real pass
writes one `audit_log` row per organization per destroyed partition (`cdr.retention.drop`, carrying
the partition name, that organization's row count, and the window that permitted it), and the counts
are gathered before the drop because afterwards there is nothing to count.

## Acceptance

Before enabling real traffic, verify public DNS, certificates, two-way media through the advertised ranges and TURN over UDP and TCP. Then use explicitly approved test endpoints for incoming/outgoing calls, organization routing, transfer, voicemail, recording, reconnection and carrier failures. Emergency calling needs verified number/address activation and Telnyx's approved test procedure; ordinary successful calls do not prove it.

Local test entry points:

- `.scripts/verify-platform-stack.mjs`: fresh migrations, real application containers, signup/verification, organization setup and extension assignments. Set `PLAYWRIGHT_MODULE` to the installed Playwright module path and `BROWSER_MEDIA_IP` to a reachable host address for two-user calling, measured audio, hold/resume, hangup, CDR persistence, media cleanup and delayed directory startup. `HOLD_DURATION_MS=35000` checks a hold longer than the default RTP watchdog. The harness uses disposable databases, synthetic accounts and a local SMTP capture server; it sends no external email or carrier calls. Build the local `optimiq-voice-audit/{api,engine,web,sipd,mediad}:local` images from each app Dockerfile first.
- `.scripts/verify-browser-calling.mts`: two SIP edges, two media nodes and the product browser adapter. Initial account lookup/admission are fixtures. Set `BROWSER_TURN_PUBLIC_IP` and `BROWSER_TURN_TRANSPORT=udp` or `tcp` for relay-only audio and relay-loss checks.
- `.scripts/verify-media-cluster.mjs`: media ownership, recording, routing across instances, teardown and owner loss.

The native deployment still has explicit release gaps in the implementation progress document, including shared-line runtime, full session refresh interoperability, conference placement and capacity, distributed limits and recovery/load proof. Do not treat building the images or passing local tests as completion of these gates.
